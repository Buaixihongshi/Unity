# wait_reply 求助闭环

依据聊天室方案 `plans/a2a-help-loop-v1.md`（张楚岚，来源任务 m_1aa76c92f0434847adac7c17c7e6d927，已读原文）。基线 6e936f4。

验收：求助 → 对应伙伴最终回复 → 发起者续答；失败、空回复和用户插话可追踪收尾。只调整普通任务 runner，不改变圆桌、fire_and_forget 去重和 #137/#158。

1. 现有 a2a/observability 四个测试文件基线 68 项通过。G1：缺少闭合检查，作为观测能力补充；G2：连续两次求助正文串轮未复现，补回归；G3：失败提示及确认声明检查缺口已确认，#184；G4：补超时结果到失败续答的 fixture 回归。另确认同一回合多次求助事件关联错误，#185。
2. invoke 记录 callee_step_id；runner 记录 a2a.step.started（实际回合、step、父 step、origin）。回复用 callee step 精确定位 invoke，取消事件携带父 step。字段均为增量，不迁移历史数据。
3. 观测按每次 invoke 检查唯一 reply/reply.failed/cancelled、被叫回合与真实消息、发起者续答；deferred 追到被叫者最终续答。进行中的等待、缺少新增关联的历史事件为 n/a，不能假报通过。
4. 失败提示由宿主事件决定，不能靠伙伴回复正文判断失败；恢复者明确确认失败伙伴已回复时，claims 检查报告矛盾。只识别窄范围明确声明，不把它当通用事实核查。
5. fixture 验正常、重复伙伴、同轮多求助、超时、空回复、嵌套、打断和损坏事件。至少两个故意改坏验证测试会失败。再在任务 development 环境按继承路由跑真实 CLI 正常链。

作者自验不算独立审阅；共享调度/协议改动提交张楚岚审查。PR 待审，不自行合并或部署。恢复可撤销此功能分支，保留原始事件与任务数据；无需数据库迁移。
